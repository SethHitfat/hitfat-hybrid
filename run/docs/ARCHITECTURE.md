Status: Phase 1 implemented on branch `claude/optimistic-wozniak-m3kjg3`. Phases 2–5 wait for Phase 1 sign-off.

## 1. Existing project audit

| Area | Finding | Consequence for HITFAT RUN |
|---|---|---|
| Framework | Static Netlify site, no build step. Each product is a single HTML file with inline JS (`index.html` ≈ 9 500 lines). Fonts Inter + Oswald. | Keep the stack: vanilla ES modules served as-is, no bundler. Split the Run app into modules so it never becomes a 9 500-line file. |
| Auth | Supabase Auth at `https://auth.hitfat.io` (project *Hitfat Hybrid*, `khuzvhtctjsnrrovjdye`). Google OAuth + email/password. `handle_new_user` trigger creates `profiles` rows. | Reuse the same project, client key and sign-in methods. **No auth configuration was changed.** One manual step: add `/run/` to Redirect URLs. |
| Data | 34 public tables, all RLS-enabled, no migration history. Hybrid stores most user state in `user_data.data` (jsonb). Existing social, club (`clubs`, `club_physical_members`, `club_sessions`, `club_attendance`), badge (`badges`, `user_badges`) and challenge tables. | All Run tables are **new and prefixed `run_`**. No existing table is altered. Hybrid's `user_data` is not reused: the Hybrid app rewrites that row whole and drops unknown keys. |
| Roles | `club_physical_members.role` (member/coach/admin) per gym; `hitfat_is_admin()` = admin of club `hitfat`. | `run_is_super_admin()` reuses `hitfat_is_admin()`. Run roles live in `run_staff` so a gym coach is not automatically a running coach. |
| Badges | Hybrid UI reads every row of `badges`; `user_badges` is readable by every signed-in user and accepts client inserts. | Not reused: adding run badges would show them in Hybrid, and client-inserted awards can be forged. `run_user_achievements` is written only by a server function. |
| Payments | Bayarcash via Netlify functions (`pay-create`, `pay-callback`, `pay-status`), prices hard-coded in `pay-create.js`, ownership in `payments` + `user_data`. `plus_entitlements` / `plus_orders` exist (empty). No subscription model. | No second billing system. Tiers (`free/plus/coach`) resolve through `run_entitled()`, which reads the existing `plus_entitlements` via a configurable `run_tier_skus` mapping. No prices in the Run app. |
| Strava | Client id in `index.html`; `strava-callback`/`strava-refresh` Netlify functions exchange codes, but **access and refresh tokens are kept in the browser and in `user_data`**. | Phase 2 must store tokens server-side (new table readable only by service role). The current Hybrid pattern is not reused. |
| Video | Vimeo ids in `const V` (`index.html:1620`), embedded via `player.vimeo.com`. | Workout templates carry `video_url`; Strength-for-Runners (Phase 3) will point at the same Vimeo ids. |
| Push | VAPID + `push_subs` + edge function `push`. | Reusable later (explicit opt-in only). Not used in Phase 1. |
| Brand | Hybrid palette is black + yellow `#FFE000`. Logo files (`icon-512.png`, `og-image.png`) are the **HITFAT HYBRID** mark; no standalone HF symbol is in the repo. | Run uses the brief's red `#E30613` / `#111111`. The header uses a text wordmark until the official HF symbol file is supplied; the existing official icon is used, unmodified, for the installed-app icon. |
| Security notes | `pay-status` returns any user's purchased program ids to anyone who passes that `user_id` (no auth check). `workout_history` has `select … using (true)` for everyone. | Out of scope here; reported separately. |

The earlier `/run` prototype (localStorage-only tracker, `run_data`/`run_club_runs` SQL) was never applied to the database. It is replaced by this design; its GPS engine is kept as the experimental tracker.

## 2. Architecture

```
/run/                       static PWA (Netlify)
  index.html                shell, loads supabase-js UMD + Leaflet from CDN
  app.css                   design tokens (light/dark), components
  sw.js                     offline shell, network-first, never caches API
  js/main.js                boot, auth gate, hash router, tab bar
  js/api.js                 every Supabase call; offline outbox for activities
  js/i18n.js                Bahasa Malaysia (default) + English strings
  js/ui.js                  formatting, sheets, toasts, icons
  js/achievements.js        bilingual badge copy (the server decides who earns them)
  js/gps.js                 experimental GPS tracker
  js/views/*.js             one module per screen
  db/001_run_club_phase1.sql   schema, RPCs, RLS (idempotent, additive)
  db/002_seed_programs.sql     generated by db/seed/programs.mjs
  db/tests/                    RLS test suite (plain Postgres + Supabase stub)
  tests/e2e.mjs                Playwright journey against Postgres + PostgREST
Supabase (existing project) — Postgres + Auth + RLS
```

Business rules that must hold no matter which client calls them run in Postgres, not in the browser: enrolment and calendar generation (`run_enroll`), rescheduling (`run_reschedule`), RSVP capacity (`run_rsvp`), achievement awards (`run_evaluate_achievements`) and data erasure (`run_delete_my_data`).

## 3. Reusable components

Reused as-is: Supabase project and session, Google/email sign-in, `profiles` (display name), `hitfat_is_admin()`, `plus_entitlements`, Inter/Oswald, the official app icon, Netlify hosting and headers.
Ready for later phases: Bayarcash functions (Plus/Coach purchases), `push` edge function, Vimeo library, `strava-callback` (to be reworked to store tokens server-side).

## 4. Database migration plan

`001_run_club_phase1.sql` (additive, idempotent, one transaction):

| Table | Purpose | Who can read / write |
|---|---|---|
| `run_chapters` | Club chapters; seeded with Kelantan | members read · super admin writes |
| `run_staff` | super_admin / head_coach / running_coach / club_captain, optionally per chapter | own rows · super admin |
| `run_profiles` | Onboarding answers incl. optional limitations (consent-gated) | owner only |
| `run_programs`, `run_workout_templates` | Coach-authored plans, bilingual jsonb, tier, draft→review→published | members read published + entitled · coaches author · **head coach publishes** |
| `run_tier_skus` | Maps Plus/Coach tiers to existing HITFAT+ SKUs | members read · super admin writes |
| `run_enrollments`, `run_scheduled_workouts` | Active plan and its calendar; completion, RPE, feedback | owner (results columns only) · created by `run_enroll()` |
| `run_activities` | Manual / GPS / Strava runs. Client-generated uuid = idempotent submit; `(user, source, external_id)` unique for imports | owner only |
| `run_club_members` | Chapter membership | own · chapter staff |
| `run_events`, `run_event_registrations` | Community runs, RSVP, capacity; `checked_in_at` reserved for Phase 4 | members read events · chapter staff manage · guest list staff-only · RSVP via `run_rsvp()` |
| `run_user_achievements` | Earned badges | owner reads · server function writes |

Plans are seeded as **`review`**: a HITFAT head coach must read and publish them in the app before any runner sees them.

## 6. Phase 1 user journey (tested end-to-end)

Sign up → onboarding → Road to 5KM recommended → calendar on chosen weekdays → open today's workout → mark complete and log the run (RPE, feeling) → progress updates → RSVP to a club run → *First Run* achievement.

## 7. Design system

- Colour: red `#E30613`, ink `#111111`, white; neutral greys; success/warning/error only for status.
- Light and dark themes (system default, override in Profile). Red text on dark uses a lighter tint for contrast.
- Type: Oswald for numbers and headings, Inter for body. Large tabular numerals for metrics.
- Layout: single column on phones, max 720 px content; side rail navigation from 900 px.
- Components: cards with 16 px radius, pill buttons, bottom sheets, empty states, skeletons, toasts.
- No gradients beyond flat brand red, no glass, no 3D.

## 9. Security & privacy

- RLS on every `run_` table; anon has no table access at all. 9 groups of permission tests in `db/tests/rls_test.sql`.
- Runners' activities, routes, profiles and calendars are owner-only. Coaches get **no** access in Phase 1; Phase 3 adds explicit athlete consent.
- Health answers (limitations) are stored only with recorded consent (database constraint). The app never gives medical clearance.
- Column-level grants stop a runner rewriting which workout a session is or forging an enrolment.
- Achievements and capacity are enforced server-side.
- "Delete my HITFAT RUN data" erases every Run row; the shared HITFAT account is untouched (full account deletion stays with HITFAT support because it also removes Hybrid data).
- No statistic is shown unless it is computed from the runner's own records; empty states otherwise.
- No secrets in the client: only the publishable Supabase key.

## 10. Dependencies & external risks

- supabase-js 2.45.4 and Leaflet 1.9.4 from CDN (pinned). OpenStreetMap tiles (usage policy: light use, attribution shown).
- Browser GPS stops when the screen locks or the browser is suspended, especially on iOS. The tracker says so before every first use and is labelled experimental.
- Speech, Wake Lock and install prompts differ between Android and iOS.
- Strava: API agreement forbids showing athletes' data to others and feeding it to AI; rate limits; app review can take weeks. Phase 2 is designed around this and Phase 1 does not depend on it.
- Training content needs HITFAT coach sign-off before launch.

## Setup

1. Supabase SQL editor: run `db/001_run_club_phase1.sql`, then `db/002_seed_programs.sql`.
2. Supabase → Auth → URL Configuration → Redirect URLs: add `https://hybrid.hitfat.io/run/` (and the Netlify preview URL while testing).
3. Make the first staff (SQL editor):
   ```sql
   insert into run_staff(user_id, role) select id, 'head_coach' from auth.users where email = 'coach@example.com';
   insert into run_staff(user_id, role, chapter_id)
     select u.id, 'club_captain', c.id from auth.users u, run_chapters c where u.email = 'captain@example.com' and c.slug = 'kelantan';
   ```
   HITFAT platform admins (`hitfat_is_admin()`) are already super admins.
4. Head coach opens *Training → Review plans* and publishes the plans.
5. Tests: `run/db/tests/run.sh` (needs local Postgres) and `node run/tests/e2e.mjs` (needs Postgres, PostgREST and Playwright; see the file header).

No new environment variables are needed for Phase 1.
